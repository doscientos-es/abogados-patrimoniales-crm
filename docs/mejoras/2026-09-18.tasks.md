# Especificación técnica: evolución del módulo de tareas LEX

## 1. Objetivo

Transformar el módulo actual de tareas en un sistema único de encargos, seguimiento y continuidad del trabajo del despacho.

Una tarea debe permitir saber:

- Qué hay que hacer.
- Quién lo ha encargado.
- Quién debe hacerlo.
- En qué expediente o lead se realiza.
- En qué estado está.
- Qué se ha hecho.
- Cuál es el siguiente paso.
- Qué dependencia o bloqueo existe.
- Qué resultado ha producido.

La entidad única será `crm_tasks`.

No se debe ampliar `crm_case_tasks` en paralelo.

---

## 2. Estado actual

Ya existe:

- `crm_tasks`.
- Relación con expedientes y oportunidades.
- Título y descripción.
- Responsable.
- Prioridad.
- Etiquetas.
- Fecha de vencimiento.
- Recordatorio.
- Tipos Tarea, Recordatorio, Evento y Plazo.
- Validación de plazos legales.
- Kanban.
- Lista.
- Calendario.
- Filtros.
- Creación y edición.
- Enlaces entre documentos y tareas.
- Plantillas de títulos.
- `crm_task_events`.
- Control de concurrencia mediante `version`.

Código principal:

```text
src/components/tareas/task-workspace.tsx
src/features/tareas/application/task-types.ts
src/features/tareas/infrastructure/supabase-tareas.ts
src/features/expedientes/ui/case-detail.tsx
```

No existe todavía:

- Detalle completo de tarea.
- Estado real `En espera`.
- Encargante visible.
- Acuse de recibo.
- Conversación.
- Evidencias.
- Resultado obligatorio.
- Continuidad al completar.
- Dependencias.
- Siguiente acción persistida en la tarea.
- INBOX personal.
- Reuniones enriquecidas.
- Permisos específicos para tareas delegadas.
- Señal fiable de expediente sin siguiente acción.

---

# 3. Decisión arquitectónica principal

## 3.1 Fuente única

`crm_tasks` será la única entidad de tareas.

`crm_case_tasks` no debe recibir nuevas funcionalidades.

Debe hacerse una de estas dos cosas:

1. Migrar los datos válidos de `crm_case_tasks` a `crm_tasks`.
2. Mantener `crm_case_tasks` temporalmente sin utilizarlo en la nueva UI.

No se deben implementar estados, históricos o resultados en ambas tablas.

## 3.2 Separar conceptos

No mezclar:

| Concepto         | Significado                               |
| ---------------- | ----------------------------------------- |
| Estado           | Situación compartida de la tarea          |
| Siguiente acción | Marca sobre una tarea viva                |
| Vencimiento      | Fecha límite de la tarea                  |
| Recordatorio     | Aviso                                     |
| Plazo legal      | Fecha profesional que requiere validación |
| INBOX            | Organización personal                     |
| Dependencia      | Bloqueo respecto a otra tarea             |

Actualmente `validation_status = proposed` se usa visualmente como “En espera”. Esto debe eliminarse.

Un plazo pendiente de validación no es una tarea esperando a un tercero.

# 4. Cambios en base de datos

Crear una migración nueva. No modificar migraciones ya aplicadas.

## 4.1 Ampliar `crm_tasks`

Añadir:

```sql
alter type public.crm_task_status
add value if not exists 'waiting';
```

Campos:

```sql
alter table public.crm_tasks
  add column if not exists is_next_action boolean not null default false,
  add column if not exists waiting_reason text,
  add column if not exists waiting_until timestamptz,
  add column if not exists waiting_detail text not null default '',
  add column if not exists completion_result text not null default '',
  add column if not exists cancellation_reason text not null default '',
  add column if not exists opened_at timestamptz,
  add column if not exists opened_by uuid references public.crm_profiles(id),
  add column if not exists rejection_reason text not null default '',
  add column if not exists rejected_at timestamptz,
  add column if not exists parent_task_id uuid references public.crm_tasks(id),
  add column if not exists meeting_details jsonb not null default '{}'::jsonb;
```

Añadir restricciones:

```sql
check (
  status <> 'waiting'
  or (
    nullif(trim(waiting_reason), '') is not null
    and waiting_until is not null
  )
)
```

```sql
check (
  status <> 'completed'
  or nullif(trim(completion_result), '') is not null
)
```

```sql
check (
  status <> 'cancelled'
  or nullif(trim(cancellation_reason), '') is not null
)
```

Los campos de espera deben limpiarse al salir de `waiting`.

La tarea debe tener siempre contexto:

```sql
check (case_id is not null or opportunity_id is not null)
```

## 4.2 Tabla de mensajes

Crear:

```sql
create table public.crm_task_messages (
  id uuid primary key default gen_random_uuid(),
  firm_id uuid not null references public.crm_firms(id),
  task_id uuid not null references public.crm_tasks(id) on delete cascade,
  author_id uuid references public.crm_profiles(id) on delete set null,
  body text not null check (char_length(trim(body)) > 0),
  message_type text not null default 'comment',
  created_at timestamptz not null default now()
);
```

Valores previstos para `message_type`:

```text
initial_assignment
comment
system
```

Debe ser append-only para los usuarios.

## 4.3 Tabla de evidencias

Crear:

```sql
create table public.crm_task_evidences (
  id uuid primary key default gen_random_uuid(),
  firm_id uuid not null references public.crm_firms(id),
  task_id uuid not null references public.crm_tasks(id) on delete cascade,
  created_by uuid references public.crm_profiles(id) on delete set null,
  body text not null default '',
  document_id uuid null,
  created_at timestamptz not null default now()
);
```

Una evidencia puede ser texto, documento o ambas cosas.

## 4.4 Tabla de dependencias

Crear:

```sql
create table public.crm_task_dependencies (
  id uuid primary key default gen_random_uuid(),
  firm_id uuid not null references public.crm_firms(id),
  predecessor_task_id uuid not null references public.crm_tasks(id) on delete cascade,
  successor_task_id uuid not null references public.crm_tasks(id) on delete cascade,
  created_by uuid references public.crm_profiles(id) on delete set null,
  created_at timestamptz not null default now(),
  unique (predecessor_task_id, successor_task_id),
  check (predecessor_task_id <> successor_task_id)
);
```

Validaciones:

- Las dos tareas deben pertenecer al mismo despacho.
- No se permiten ciclos.
- Una tarea bloqueada no puede aparecer como ejecutable.
- Al completar el antecedente se desbloquea la sucesora.

## 4.5 Tabla de INBOX personal

Crear:

```sql
create table public.crm_task_inbox_items (
  id uuid primary key default gen_random_uuid(),
  firm_id uuid not null references public.crm_firms(id),
  user_id uuid not null references public.crm_profiles(id) on delete cascade,
  task_id uuid null references public.crm_tasks(id) on delete cascade,
  capture_text text not null default '',
  stage text not null default 'inbox',
  position integer not null default 0,
  created_at timestamptz not null default now(),
  updated_at timestamptz not null default now()
);
```

Valores de `stage`:

```text
inbox
clarify
delegate
next
now
waiting
weekly_review
```

Mover una entrada en esta tabla no debe modificar `crm_tasks.status`.

## 4.6 Reuniones

Usar `kind = event`, pero guardar los datos específicos en `meeting_details`.

Estructura mínima:

```json
{
  "startsAt": "...",
  "endsAt": "...",
  "mode": "office_bilbao",
  "location": "Despacho Bilbao",
  "meetingUrl": "",
  "preparation": "",
  "attendeeContactIds": [],
  "attendeeUserIds": ""
}
```

Valores mínimos de modalidad:

```text
office_bilbao
office_recalde
phone
outside_office
```

# 5. RPCs obligatorias

El RPC actual `crm_update_task` es demasiado genérico. Las transiciones de negocio deben separarse.

## 5.1 Crear tarea

```text
crm_create_task
```

Debe:

- Validar título.
- Validar contexto.
- Validar responsable activo.
- Crear la tarea.
- Crear el mensaje inicial si existe.
- Registrar evento `created`.
- Permitir marcar siguiente acción mediante una operación separada.

## 5.2 Abrir tarea

```text
crm_open_task
```

Debe:

- Guardar `opened_at`.
- Guardar `opened_by`.
- Ejecutarse solo la primera vez.
- Registrar evento `opened`.
- No cambiar el estado.

## 5.3 Cambiar estado

```text
crm_set_task_status
```

Debe aceptar:

```text
pending
in_progress
waiting
completed
cancelled
```

Reglas:

- `waiting` exige motivo y fecha.
- `completed` exige resultado.
- `cancelled` exige motivo.
- Registrar cada transición.
- Validar permisos.
- Comprobar `version`.
- No sobrescribir cambios concurrentes.

## 5.4 Poner en espera

```text
crm_put_task_on_hold
```

Parámetros:

```text
task_id
expected_version
reason
review_at
detail
```

Debe:

- Cambiar a `waiting`.
- Guardar motivo y fecha.
- Sacar la tarea del trabajo ejecutable.
- Registrar evento `waiting_started`.

## 5.5 Reactivar tareas en espera

```text
crm_reactivate_waiting_tasks
```

Debe:

- Buscar tareas `waiting` cuya fecha haya llegado.
- Registrar evento `waiting_review_due`.
- Hacer que vuelvan a aparecer como trabajo pendiente.
- Ser idempotente.
- Respetar la zona horaria de Madrid.
- No completar ni duplicar tareas.

## 5.6 Completar

```text
crm_complete_task
```

Debe:

- Exigir resultado.
- Cambiar a `completed`.
- Registrar evento.
- Desbloquear dependencias en la misma transacción.
- Si era siguiente acción, devolver al frontend una decisión obligatoria:

```text
create_next_task
close_without_continuity
```

No debe crear automáticamente la siguiente tarea sin elección explícita.

## 5.7 Siguiente acción

```text
crm_set_next_action
```

Debe:

- Marcar o desmarcar `is_next_action`.
- Bloquear el contexto.
- Desmarcar la siguiente acción anterior.
- Garantizar una única siguiente acción abierta por contexto.
- Registrar evento.

## 5.8 Delegación

Crear o modificar RPCs para:

- Reasignar.
- Registrar rechazo.
- Registrar reclamación.
- Registrar cambios de plazo.
- Registrar cambios de prioridad.
- Registrar cambios de encargo.

## 5.9 Mensajes

```text
crm_add_task_message
```

Debe:

- Validar acceso a la tarea.
- Insertar mensaje.
- No permitir editar o borrar mensajes de otros usuarios.
- Registrar autor y fecha.

## 5.10 Dependencias

```text
crm_create_task_dependency
crm_remove_task_dependency
crm_complete_and_unlock
```

Deben:

- Evitar ciclos.
- Validar mismo despacho.
- Bloquear la sucesora.
- Desbloquear automáticamente cuando corresponda.

# 6. Permisos

La UI debe reflejar los permisos, pero la validación definitiva debe estar en el servidor.

| Acción              | Encargante |    Responsable |    Admin / abogado |  Consulta |
| ------------------- | ---------: | -------------: | -----------------: | --------: |
| Leer                |         Sí |             Sí |     Según contexto | Según RLS |
| Comentar            |         Sí |             Sí |                 Sí |        No |
| Cambiar título      |         Sí |             No |                 Sí |        No |
| Cambiar descripción |         Sí |             No |                 Sí |        No |
| Cambiar plazo       |         Sí |             No |                 Sí |        No |
| Cambiar prioridad   |         Sí |             No |                 Sí |        No |
| Reasignar           |         Sí |             No |                 Sí |        No |
| Poner en espera     |         Sí | Según decisión |                 Sí |        No |
| Completar           |         Sí |             Sí |                 Sí |        No |
| Rechazar            |         Sí |  Sí con motivo |                 Sí |        No |
| Cancelar            |         Sí | Según decisión |                 Sí |        No |
| Validar plazo legal |         No |             No | Owner/admin/lawyer |        No |

El responsable debe ver los campos protegidos deshabilitados con una explicación, por ejemplo:

> El plazo solo puede modificarlo quien encargó esta tarea.

- Evidencia opcional.
- Documento opcional.

  - `Crear siguiente tarea`.
  - `Cerrar sin continuidad`.

## 7.7 En espera

Abrir diálogo:

- Motivo obligatorio.
- Revisar el día obligatorio.
- Detalle obligatorio o recomendado según decisión final.

Al confirmar:

- Cambiar a `En espera`.
- Mostrar fecha de revisión.
- Retirar del trabajo ejecutable.
- Registrar histórico.

# 8. Integraciones

## Expediente

Debe mostrar:

- Tareas abiertas.
- Siguiente acción real.
- Tareas bloqueadas.
- Tareas en espera.
- Señal `Sin siguiente acción`.

No debe tratar `crm_cases.next_action` como sustituto de una tarea.

## Lead

Debe utilizar la misma tarea global.

## Calendario

Debe leer los mismos registros de `crm_tasks`.

Modificar una fecha en calendario debe actualizar la tarea, y viceversa.

No crear eventos duplicados.

## Fechas y plazos

Cada fecha debe poder abrir su tarea origen.

## Documentos

Desde la tarea:

- Vincular documento.
- Desvincular documento.
- Abrir documento.
- Ver versión.

Desde el documento:

- Ver tareas relacionadas.
- Crear tarea vinculada.

## Dashboard

Actualizar contadores para:

- Pendientes.
- En curso.
- Vencidas.
- En espera.
- Sin abrir.
- Sin siguiente acción.

Los plazos propuestos no deben contabilizarse como tareas en espera.

# 11. Definition of done

El módulo no se debe considerar terminado solo porque compile o pase los tests de componentes.

Debe existir evidencia de:

1. Migración aplicada.
2. RPCs probadas.
3. RLS probado por roles.
4. Tests automatizados.
5. Prueba manual autenticada.
6. Tarea propia.
7. Tarea delegada.
8. Expediente activo.
9. Tarea en espera.
10. Plazo legal.
11. Dependencia.
12. Continuidad.
13. Calendario.
14. Documento vinculado.

La primera entrega recomendable es:

```text
Fuente única
+ Estado En espera
+ Detalle de tarea
+ Cierre con resultado
+ Siguiente acción
+ Continuidad
+ Histórico
+ Permisos de delegación
```

INBOX, reuniones avanzadas y Google Calendar deben venir después del núcleo operativo.
